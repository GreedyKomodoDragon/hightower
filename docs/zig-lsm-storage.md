# Minimal Zig key-value storage

`hightower.storage.Database` is a custom local format, not a Pebble-compatible database. `open(allocator, io, parent_dir, path)` takes an exclusive process lock and owns the opened subdirectory until `close`. `get` returns caller-owned bytes. `put`, `delete`, and `write` accept binary keys; `write` makes all operations in its slice visible together. `scan` returns an owned, sorted page from `[lower, upper)` with an optional exclusive `after` cursor, a row limit, and a byte limit. Free pages with `Database.freeRows`. `snapshotKeys` copies and sorts all live keys in a range once for batched mutation; free that snapshot with `Database.freeKeys`. `flush` and `compact` are also available for maintenance.

Each successful batch is checksummed, written to the write-ahead log, and synced before it is visible to readers. The mutable in-memory table rotates at 64 MiB. Flushing writes a sorted immutable table, syncs it and the directory, then atomically replaces and syncs the manifest before retiring the old log. Four same-level tables are merged into a higher level. A full `compact` replaces all tables with one table of live keys and removes tombstones only after the new manifest is durable. Column pruning also triggers this reclamation when at least 128 deleted keys accumulate and they reach one quarter of the live-key count. Recovery replays complete log records, discards an incomplete final record, validates table records and the manifest, and removes files not named by the manifest. A failed write or sync can have an ambiguous outcome after a crash; reopen and read the key before retrying an operation that is not naturally idempotent.

Keys are limited to 4 KiB, values to 10 MiB, and batches to 16 MiB. One process owns the directory; concurrent readers and one writer use an internal read/write lock. Compaction currently runs synchronously, and the in-memory index contains one entry per key. This keeps the first format small but means large compactions can pause writes and RAM use grows with key count. `scan` pages are bounded, but constructing a page sorts the current key index. `snapshotKeys` sorts and retains the whole selected key range in memory until the caller frees it; column pruning uses one snapshot of expired slot keys per call. The database has no compression, long-lived read snapshots, multi-process access, or Pebble file compatibility. The format currently targets Linux and macOS filesystem behavior.
