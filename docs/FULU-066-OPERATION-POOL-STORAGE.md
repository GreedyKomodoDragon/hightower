# FULU-066: Durable consensus operation pool design

Decision for [#124](https://github.com/GreedyKomodoDragon/hightower/issues/124): use a separate `operations` namespace in Hightower's existing [checksummed key-value database](zig-lsm-storage.md). This is a design; the pool and runtime still operate in memory.

## Current behavior and choice

[`Pool`](../src/consensus/operation_pool.zig) owns attestations, proposer slashings, attester slashings, signed voluntary exits, and signed BLS-to-execution changes. Admission validates against a copied beacon state; attestation admission may merge disjoint participants with matching data. Each list is sorted by SSZ root and capped at twice its block limit. Selection validates candidates again in block order. `accepted` removes exact included roots. Attestations expire after one epoch, but expiry currently runs only on attestation admission; other invalid entries are pruned only when their list fills. No production runtime owns this pool yet. The runtime saves `fork-choice.bin`, which has a 256 MiB limit and contains blocks and states, but no pool entries. The existing database has synced atomic batches, binary keys, 10 MiB values, and 16 MiB batches.

| Requirement | Add pool to fork-choice snapshot | Separate database namespace (chosen) |
| --- | --- | --- |
| Admission cost | Serialize and replace the whole snapshot for each accepted operation, including retained blocks and states. | One small synced batch per admission; a merge replaces two keys in one batch. |
| Interrupted write | Atomic file replacement retains either old or new snapshot. A failed save may have an uncertain outcome. | Complete checksummed log batches replay; an incomplete trailing batch is discarded. A failed sync may still have an uncertain outcome. |
| Duplicates and ordering | Decode all entries and rebuild a root index; snapshot replacement must serialize the pool with every choice update. | Type and root form the key; repeated writes are idempotent. Rebuild sorted lists from records. |
| State changes, expiry, reorg | Revalidate after loading; every removal rewrites the snapshot. Snapshot and pool share one atomic file. | Revalidate after loading; delete expired, included, or invalid keys in bounded batches. Reconcile the separate store with accepted block history before proposals. |
| Version and corruption | Any incompatible pool addition changes the fork-choice file format; a corrupt pool can make the chain snapshot unavailable. | Version each pool record; reject a bad record without changing the readable fork-choice snapshot. Database manifest or table corruption still requires database recovery. |
| Space and operations | One file with a fixed limit, but repeated full rewrites. | Per-type count limits plus byte limits and periodic compaction; a second store lifecycle and cross-store reconciliation. |

The separate namespace costs an additional open/close and recovery path. It avoids changing the fork-choice snapshot format or paying its write cost on every admission. It also keeps pool corruption from making the chain snapshot unreadable.

## Durable model and bounds

Open one database below the node data directory with an exclusive owner. Reserve binary key prefix `operations/v1/`, followed by a one-byte type tag and the 32-byte SSZ hash-tree root of the signed operation. Store one record per key: schema version, type, root, SSZ byte length, and exact SSZ bytes. Validate the key against the record and recomputed root on load. The database supplies checksums and atomicity; the record header supplies schema and type checks. Reject unknown versions and types, malformed lengths or SSZ, and oversized values. Keep these rejected records out of memory and report them for diagnosis; do not silently reinterpret a newer schema. A migration tool or later implementation can explicitly convert supported old versions.

Persist no sorted position, derived attesting indices, validation cache, or beacon-state copy. Rebuild order by root and recompute validation metadata against the current state. Treat an identical type/root/bytes record as a duplicate. A root collision with different bytes is corruption and must not replace the existing record. For merged attestations, atomically delete the old root and insert the validated merged value; a crash yields either old or merged evidence. The pool's existing admission rules, including conflict checks, remain authoritative.

Use the existing per-type caps of twice each preset's block limit; enforce them before durable admission and again while recovering. Add a total encoded-byte budget and a per-record maximum no larger than the database's 10 MiB value limit. Set the budget from the sum of each type's maximum SSZ size times its pool cap, with checked arithmetic, so the bound works for both minimal and mainnet presets. Reject admissions that exceed it. Recovery must never allocate beyond those limits, even if disk has extra keys. Delete expired attestations as slots advance, and delete entries invalid against the current state during periodic pruning, not only on a later admission. Batch tombstone cleanup and compact when deletion thresholds are met; enforce the byte budget on live records while compaction reclaims physical space. Physical disk use can temporarily exceed the live budget until compaction completes; surface compaction failures and avoid unbounded admission if storage cannot be reclaimed.

## Write, acceptance, and recovery order

1. Validate an admission against a stable current beacon state, check conflicts and capacity, encode its signed SSZ value, and compute its root. Hold the pool's serialization lock across the final duplicate/capacity check, database write, and memory update.
2. Commit and sync the database batch before exposing the new or merged operation in memory or acknowledging admission. On a write or sync error, do not publish the candidate; mark the pool unavailable for further writes until reopening and reconciling the database. The batch may have committed despite the error. Reopen and inspect the key or keys before retrying; type/root keys and atomic merge batches make this safe. An incomplete trailing log record is ignored on recovery.
3. Once a block is accepted and its fork-choice snapshot is durable, delete its included operations in one or more synced batches, then remove them from memory. Never remove on a proposal or rejected block. If deletion fails, stop pool writes and proposals until recovery; a stale durable entry must not be proposed again. The existing in-memory `accepted` method does not provide this ordering and needs integration work.
4. On restart, load the durable fork-choice snapshot and its current beacon state first. Open and scan the operation namespace in bounded pages. Check every record's schema, lengths, type, key/root, and SSZ decoding; reject corrupt, partial, unsupported, duplicate, or over-limit records. Revalidate survivors against the current state and replay admission rules in deterministic root order, including attestation conflicts and merges. Drop expired and now-invalid records with synced deletes. Rebuild sorted lists and derived metadata.
5. Before enabling proposals, reconcile recovered entries with every retained accepted block that may have been saved before its pool deletion. Remove exact included operations and revalidate survivors against the selected head. A canonical reorg does not automatically resurrect operations removed by an accepted side-branch block: recover useful operations from retained displaced blocks only through the normal admission path, with current-state validation and capacity checks. If block history is insufficient for safe reconciliation, keep proposals disabled until a trusted resync or discard and rebuild the pool from peers. Fork-choice remains the authority for chain state.

The two stores do not share a transaction. Snapshot-first, pool-delete-second ordering makes a crash leave at most stale pool entries, which reconciliation removes. An uncertain snapshot save outcome requires reloading the snapshot before pool deletion. A pool failure does not alter the chain snapshot. Database-level corruption that prevents opening the store requires operator recovery or a fresh empty pool; it must not be treated as a valid partially recovered pool.

## Migration and implementation sequence

Existing nodes have no durable pool records. On first upgrade, create an empty operation namespace and leave the existing `fork-choice.bin` readable without format changes. The in-memory pool, if any, may be re-admitted through the durable path before acknowledging new work; a process restart before that loses those old entries as it does today. Downgrading leaves the namespace unused by older binaries. No execution transaction pool data is moved.

1. **[FULU-108: operation pool store](https://github.com/GreedyKomodoDragon/hightower/issues/224).** Implement the versioned codec, limits, synced put/delete/merge batches, bounded scan, corruption handling, and storage tests using the existing database. Depends on this design and the database contract; does not change `fork-choice.bin`.
2. **[FULU-109: operation pool runtime integration](https://github.com/GreedyKomodoDragon/hightower/issues/225).** Give the production node one pool owner, wire admission, slot pruning, accepted-block deletion, startup revalidation and block reconciliation, proposal gating, and reorg re-admission. Depends on the store ticket and runtime/fork-choice persistence work in [#39](https://github.com/GreedyKomodoDragon/hightower/issues/39). The [execution transaction pool](https://github.com/GreedyKomodoDragon/hightower/issues/73) remains separate.

## Required implementation tests

- A crash before sync, after sync but before memory publication, during merge, and between snapshot save and pool deletion produces the documented old/new batch outcome and never proposes an included operation after restart.
- Failed or ambiguous sync requires reopen and key inspection before retry; duplicate admissions remain idempotent, and same-root/different-bytes records are rejected.
- Truncated log tails, malformed or partial values, bad checksums, wrong type/root, unknown schema versions, and oversized records are rejected without returning a partial in-memory pool; the fork-choice snapshot remains readable.
- Recovery from changed beacon state, advanced slots, full per-type lists, and deterministic attestation merges revalidates, expires, prunes, and sorts the same survivors as fresh admission.
- Canonical inclusion, accepted side branches, reorgs, and retained-block reconciliation preserve only currently useful operations; proposals stay gated when reconciliation cannot finish.
- Repeated admission/removal cycles obey count and byte budgets, reclaim tombstones through compaction, and surface storage failures without unchecked disk growth.
